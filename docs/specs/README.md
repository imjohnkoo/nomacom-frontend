# 기능정의서 (Feature Definition Document) — 작성 가이드

> **무엇**: nomacom-admin / nomacom-client / nomacom-mobile 에 **신규 기능을 만들기 전에** 사용자의 _목적 → 단계 → UI_ 를 합의해두는 문서.
> **왜**: "무엇을 만드는지"를 코드 작성 전에 **정확히 같은 그림**으로 맞추기 위해. 구현(Plan)과 전략(Proposal) 사이의 빠진 고리.
> **이 폴더**: `docs/specs/` — 복사용 템플릿 `_template.html` + 실제 작성물. `docs/specs/`·`docs/plans/` 는 **git 공유**(`.gitignore` 예외, 2026-09-02 전환), 나머지 `docs/`(proposals·research 등)는 로컬 전용.

---

## 1. 핵심 아이디어 — 3레이어 하이브리드

하나의 방법론으로 _목적 + 단계 + UI_ 를 다 잡는 건 없다. 그래서 검증된 3가지를 한 문서에 합친다. **이건 한국 SI 의 `기능정의서 + 화면정의서` 전통과 1:1로 맞는다.**

| 레이어 | 출처 방법론                                   | 무엇을 잡나                                                                              | 템플릿 섹션                           |
| ------ | --------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------- |
| 상단   | **JTBD** (Job Story)                          | 사용자 **목적** — "언제 / 무엇하려고 / 어떤 결과 기대"                                   | §2 사용자와 목적                      |
| 중단   | **Use Case** main success scenario + 예외흐름 | **단계** — 번호 매긴 정상 경로 + 분기                                                    | §3 사용자 시나리오 / §4 기능 요구사항 |
| 하단   | **화면정의서** (Screen spec)                  | **UI** — 화면별 상태(Empty/Loading/Error/Success/권한) + 이벤트 + 예외 + 부분성공·비동기 | §5 화면정의                           |

- 주문 소유권·PII 노출 같은 규칙은 "화면에서 숨김"으로 끝나지 않는다 — 서버 측 **불변식**(절대 안 됨 규칙)을 §4 전제조건 표에 못 박는다.
- 다건 발급(멀티 QR) 같은 best-effort 기능은 Success 를 **전체성공 / 부분성공 / 전체실패**로 쪼개 §5 부분/특수 상태에 적는다.
- 단계(§3)는 **분기·상태전이가 많으면 Mermaid 플로우차트**, **단순 선형이면 번호 목록**.

## 2. 언제 쓰나 (적용 범위 = T2 트리거)

**필수** — 다음 중 하나라도 해당하면 코드 전에 기능정의서를 먼저 쓴다. 이 목록이 곧 `nomacomfe-spec-session` 의 **T2 트리거**다:

- 🆕 **신규 화면** (새 페이지 / 모달 / 드로어 / 대시보드)
- 🔀 **신규 사용자 플로우** (여러 단계를 거치는 새 동선 — 발급·환불·재발급 등 상태 전이가 있는 것)
- 🔌 **외부 연동 변경** (**Maya eSIM B2B API** / 네이버 스마트스토어 Commerce API / Cafe24 / PG — 사용자에게 보이는 동작이 바뀔 때)
- 🗄 **DB 스키마 변경** (Drizzle schema — prod DB 는 TypeORM camelCase 라 정합 주의)
- 💳 **과금·PII 경로** (주문/고객 정보를 읽거나 쓰는 변경)
- 📱 **mobile 신규 화면** (Expo Router 라우트 추가)

**면제** — 기존 Plan 으로 충분, 기능정의서 불필요:

- 버그픽스(파일 수 무관) · 리팩터 · 성능 개선 · 의존성 bump
- 카피/문구만 변경, 스타일/레이아웃 미세 조정
- 사용자에게 안 보이는 내부 변경 (마이그레이션, 로깅, 빌드)
- **`design/` 캔버스 산출물** — 상세페이지 섹션·썸네일은 별도 축(D 트랙). spec 대신 **오너 승인**이 게이트다 (§2.5)

> 애매하면 §2 사용자와 목적 · §5 상태 블록 · §6 범위 밖 **3개만** 5분 안에 써본다. 안 써지면 면제 대상일 가능성이 높다.

### 2.5 D 트랙 — `design/` 캔버스는 Tier 체계 밖이다

상품 상세페이지 섹션, 대표 썸네일 등은 코드가 아니라 디자인 산출물이다. spec LOCK / 적대적 코드 리뷰 / 회귀 테스트를 요구하면 과잉이다. 대응물만 다르게 둔다:

| 코드 트랙         | D 트랙 대응물                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------ |
| spec LOCK (사람)  | **오너 승인** (디자인 확정 ack)                                                            |
| ⑥ 적대적 리뷰     | 해당 없음                                                                                  |
| ⑦ acceptance walk | **렌더 대조** — Orca 브라우저로 실제 렌더 + 승인본 대비                                    |
| 회귀 테스트       | 해당 없음 — 대신 **슬라이더 런타임 값이 아니라 소스 기본값에 반영됐는지** 확인이 종결 조건 |
| Tier pill         | `D`                                                                                        |

### 자주 빠뜨리는 차원 (체크리스트)

해당하면 템플릿의 표시된 칸을 꼭 채운다:

- **의존성 / 선행조건** (선행 마이그·시드·배포순서·branch-from) → §1.5. **외부 연동이 끼면 절대 생략 금지** ("빌드 가능해 보이지만 실제론 막힌" 1순위 원인).
- **전제조건 / 보안 불변식** (주문 소유권 검증·적격 상태) → §4 전제조건 표. UI 숨김이 아니라 서버 규칙으로.
- **PII 노출 / 마스킹** → §4 전제조건 표의 한 행. 없으면 "PII 없음" 명시. (Secret·PII 규칙 일반은 `.claude/rules/ssm-paths.md`)
- **데이터 신선도** (실시간 / 폴링·캐시 / 일배치) → §5 화면 헤더 신선도 pill.
- **부분성공 / 비동기 / 도메인 상태** → §5 부분·특수 상태 셀. (다건 eSIM 발급에서 일부만 성공하는 경우 등)
- **확인·undo** (비가역 액션) → §5 요소·이벤트 표. (개통일 확정·취소 등)
- **비기능·한계** (데이터량·페이지네이션·상한) → §6 비기능/한계.
- **완료기준(DoD)** — 신규 플로우면 §7 에서 생략 금지. 성공지표는 생략하려면 **"측정하지 않기로 결정"을 §7 에 명시**.
- **E2E 검증 절차** — §7 마지막. 구현·QA 세션이 그대로 따라 돌릴 스텝(준비→정상경로→상태/예외→데이터 대조). **LOCK 조건**.

### eSIM 도메인 카피 규칙 (위배 금지)

기능정의서의 UI 카피는 아래 사실을 위배할 수 없다 (memory 규칙):

- **사용일수는 자정이 아니라 첫 연결 시점부터 24h rolling** 으로 차감된다
- **다국가 상품은 개통 후 자동 로밍** — 국가별 재개통 안내 금지
- 리뷰 발췌는 **전면 긍정 리뷰만** (5★여도 부정 언급이 섞이면 제외)

### 상태 · 표기 어휘

- **문서 상태 pill**: `draft`(작성중) → `locked`(합의완료) · `as-built`(현행 정리)
- **Tier pill**: `T2` / `T3` / `D` — 헤더에 필수. `nomacomfe-finish-branch` Step 0 이 이 값으로 QA 게이트 적용 여부를 판정한다
- **등급색**: `sev-high`(빨강) / `sev-med`(주황) / `sev-low`(회색)

## 3. 누가 쓰나 (역할)

"작성자 소유"가 아니라 **리드 관점**이다 — 1인 다역이면 한 사람이 다 쓴다.

| 섹션                                                             | 리드       | 보강                                      |
| ---------------------------------------------------------------- | ---------- | ----------------------------------------- |
| §1 배경 / §1.5 의존성 / §2 목적 / §3 시나리오 / §4 기능 요구사항 | **기획자** | 개발자가 실현 가능성·전제조건·엣지 피드백 |
| §4 전제조건·불변식 / §5 화면정의 (상태/이벤트/예외)              | **개발자** | 기획자가 카피·동선 확인                   |
| §6 범위 밖·한계 / §7 성공지표·DoD / §8 결정사항                  | 함께       | —                                         |

> **유일한 hard rule**: 누가 쓰든 **§2 사용자와 목적 · §5 상태 블록 · §4 보안 불변식**은 거르지 않는다. 1인 작성이어도 이 3개가 이 문서의 존재 이유.

## 4. 파이프라인 위치

```
Proposal (RFC)        →   기능정의서 (이 문서)      →   Plan (PR 단위)        →   PR / 구현
"이걸 해야 하나?"          "사용자가 정확히              "어떻게 코딩하나?"
 어떤 패턴/선례?"           무엇을 보고 무엇을 하나?"      파일별 변경·체크리스트
 (전략·의사결정)            (목적+단계+UI 합의)           (개발용)
```

- **독립 신규 문서 타입.** Proposal 을 대체하지 않는다(목적이 다름).
- **큰 기능(T3)**: Proposal 다음, Plan 앞에서 작성.
- **작은 기능**: Proposal 을 건너뛰고 기능정의서로 바로 시작하거나, Plan 에 흡수해도 됨.
- **경계**: 외부 연동의 _세부_(host/auth/결과코드 구현)는 **Plan** 으로. 기능정의서엔 *사용자 영향*만.
- Weekly HTML plan(`docs/plans/weekly/`)과는 별개 트래킹 레이어 — 무관.

## 5. 어디에 / 어떤 포맷

| 종류                                    | 위치                                                                                                  |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| app-specific                            | `docs/specs/<app-name>/YYYY-MM-DD-<topic>.html` (예: `docs/specs/client/2026-09-05-refund-flow.html`) |
| 크로스앱 (admin+client+mobile, DS 영향) | `docs/specs/YYYY-MM-DD-<topic>.html` (앱 서브폴더 없이)                                               |
| 복사용 템플릿                           | `docs/specs/_template.html`                                                                           |

- **포맷 = HTML** (임베디드 CSS, 템플릿 그대로). 상태 블록·기능ID 표가 카드/pill 로 훨씬 잘 읽힘.
- **`.md` 동반 규칙**: 루트 CLAUDE.md 는 plan/proposal 에 `.md` + `.html` 이원 산출을 요구한다. spec 도 같은 규칙을 따르되, **`.md` 는 HTML 의 축약이 아니라 같은 내용의 기계 친화 버전**이다 — LOCK 게이트가 `[NEEDS CLARIFICATION]` 마커를 grep 으로 확인하므로 `.md` 가 있으면 검사 비용이 낮다. 둘 중 하나만 고치는 것은 금지 (이중 진실).
- 분기 거의 없는 아주 작은 기능은 `.md` 단독도 무방.
- `apps/*/docs/` **생성 금지**. 모든 문서는 루트 `docs/` 하위.
- `docs/specs/`·`docs/plans/` 는 **git 공유**라 spec 파일이 PR 에 함께 올라간다. PR 설명에는 **spec 경로 링크 + 핵심 결정 1~2줄**을 붙인다.

## 6. 라이프사이클

> 전 과정은 **`nomacomfe-spec-session` 스킬**이 스테이지 게이트로 안내한다 (Tier 판정 → 실측 조사 → 인터뷰 → spec 작성 → LOCK → plan → 핸드오프). 아래는 그중 문서 라이프사이클 부분.

1. `_template.html` → `docs/specs/<app>/YYYY-MM-DD-<topic>.html` 복사 (헤더에 **Tier pill** 기록)
2. §1~4 초안 → §4 전제조건·§5 보강 (상태 pill = `draft`). 인터뷰 중 보류된 답은 `[NEEDS CLARIFICATION: 질문]` 마킹 — 가정으로 메우지 않는다
3. **LOCK 조건 6항** — 전항 충족해야 `locked` 로 전환:
   1. §8 open 결정 **0건**
   2. `[NEEDS CLARIFICATION]` 마커 **0개** (grep 확인)
   3. §2 · §4 불변식 · §5 상태 블록 · §6 채워짐
   4. §7 DoD + **E2E 검증 절차** 존재
   5. §7 성공지표 or **"측정 안 함" 명시**
   6. 헤더 **Tier pill** 기록 + 사람 ack (1인 모드는 self-ack)
4. LOCK 후 **Plan(PR 단위)** 작성 (`nomacomfe-write-plan` — 테스트 계획 3요소 포함) → 구현 착수
   - **PR base = `main` (항상).** `prod` 승격은 별도 휴먼 단계(`nomacomfe-prod-push-check` / `nomacomfe-finish-branch`). Plan 문서에 base 를 `prod` 로 적지 말 것.
5. 구현 중 스펙이 바뀌면 → **문서를 먼저 고치고**(특히 §6 범위) 헤더 **수정이력에 한 줄 추가** → 코드가 따라가게 함

## 7. 작성 예시 (요약본)

> 실제 문서는 HTML 템플릿으로 작성하지만, 감을 잡기 위한 압축 예시. (가상의 client 기능)

**[개통일 변경] 기능정의서** · `draft` · `T2` · `apps/client`

- **§1 배경**: 여행 일정이 바뀌어도 이미 확정한 개통일을 스스로 못 바꾼다. 고객센터 문의로만 처리돼 응답까지 반나절이 걸린다.
- **§1.5 의존성**: Maya `change_esim` 엔드포인트 사용(신규 백엔드 없음) · 미개통(`not_active`) 상태에서만 가능.
- **§2 목적 (JTBD)**: "출국 일정이 바뀌었을 때, 여행자는 아직 개통되지 않은 eSIM 의 시작일을 직접 옮기고 싶다, 그래서 데이터가 도착 전에 소모되지 않게 한다."
- **§3 시나리오**: 1) 주문 조회(verify) → 2) view 화면에서 '개통일 변경' → 3) 날짜 선택 → 4) 확인 모달 → 5) 변경 완료 토스트.
  - _3a._ 이미 개통됨 → 변경 불가 안내 + 고객센터 동선.
  - _4a._ Maya 응답 실패 → 원복 후 재시도 안내.
- **§4 기능 요구사항**: `F-1` 변경 가능 여부 판정(서버) · `F-2` 날짜 선택(과거 불가, 오늘 -24h 버퍼) · `F-3` Maya 반영 + 로컬 주문 갱신.
  - **전제조건·불변식**: 주문 소유권은 주문번호+이름+전화 3요소로만 검증(클라 신뢰 금지) · 노출 PII = 전화번호(마스킹) · 개통 후에는 서버가 거부.
- **§5 화면정의** `S-1 view` (접근: verify 통과 세션 / 신선도: 요청 시 실시간):
  - 상태 — _Empty_: 해당 없음 / _Loading_: 버튼 스피너 / _Error_: "변경하지 못했습니다 · 재시도" / _Success_: "개통일이 N월 N일로 변경되었습니다" / _권한_: 세션 만료 시 verify 로 / _부분_: 다건 주문에서 일부만 변경 성공 시 건별 결과 표시.
  - 확인·undo — 변경은 confirm 모달, 되돌리기는 같은 플로우 재실행.
  - 예외 — 이미 개통된 eSIM 은 버튼 자체를 disabled + 사유 툴팁.
- **§6 범위 밖 / 한계**: 개통 후 일시정지, 국가 변경은 범위 아님. 한계: 변경 횟수 상한 없음(1차).
- **§7 성공지표 / DoD**: 개통일 관련 문의 건수 ↓ / DoD: 타인 주문 접근 차단 확인 · 날짜 경계(오늘 -24h) 단위테스트 · 빌드·typecheck 통과.
- **§7 E2E 검증 절차**: ① `yarn workspace nomacom-client run dev` + 미개통 주문번호 준비 → ② view 진입 → 개통일 변경 → 날짜 D+3 선택 → 성공 토스트 확인 → ③ 개통된 주문으로 같은 시도 → 버튼 disabled 확인 → ④ DB `orders` 행의 시작일이 D+3 인지 대조.
