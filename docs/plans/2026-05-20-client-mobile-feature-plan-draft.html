1. 한 줄 요약 / 핵심 결정 포인트

현재 클라이언트(apps/client)는 깡통 빌드. 깡통 직전 상태(=GitHub nomacom-client-nuxt3)는 "네이버 스마트스토어 주문 + 수령자 정보 인증 → Maya 회선 발급 → QR 표시" 단방향 1회성 플로우. 회원/세션/결제 모두 없고, DB 도 order/esim/plan/plan-type 4 테이블뿐 (user 테이블 없음, FK 없음). 모바일은 iOS Universal Link 데모만 있는 깡통. 이번 계획은 다음 4가지를 더한다.

① 회원가입 / 로그인

자체 계정 + 소셜(Naver / Kakao / Apple) 로그인. 네이버 스마트스토어 주문번호로 들어오는 게스트 흐름도 그대로 유지하되, "내 계정에 이심 보관" 옵션을 게스트 흐름 끝에 자연스럽게 노출.

② 자체 이심 발급 (Maya 직접)

스마트스토어 매개 없이, 앱 안에서 플랜 카탈로그 → 결제 → Maya assign → QR 표시. v1 의 "주문확인 후 QR" 흐름과 병렬 운영. v1 흐름은 게스트 채널로 유지.

③ 보유 이심 추가 / 관리

내 이심 목록, 사용 시작 / 정지, 잔여 데이터 조회, 일정 재설정, 토픽업, QR 재발급. Maya B2B 정책상 ESIMmany 가 회선 ON 시점·속도·갱신을 통제하므로 UI도 우리 정책 기준.

④ 웹앱·모바일앱 듀얼 트랙

웹앱은 Nuxt SSR · 400px 모바일 우선 유지. 모바일은 Expo 로 동일 IA · 동일 디자인 토큰을 공유하고, "내 폰에 즉시 설치" UX 만 네이티브 Universal Link 로 차별화.

전제 — 이 문서는 아직 "초안". 우선순위(③ 보유 이심 관리부터 / ② 자체 발급부터), 결제 PG 선택, 인증 채널 우선순위, 앱 출시 vs 웹 PWA 우선 등 굵직한 결정은 4-Phases 회의 1회 후 확정.

2. 레거시 코드 진단 rev2

2.1 가장 최근 운영 client (imjohnkoo/nomacom-client-nuxt3 · 2026-02-24 last push)

GitHub 상의 진짜 최신 client. Nuxt 3 + Nitro server + Drizzle + postgres + Maya API 직접 호출. monorepo 의 apps/client 깡통 직전 상태와 (Nuxt 4 마이그 차이 외) 동일.

아키텍처

[Browser] ↓ /verify/:orderId, /details, /select-date, /view (Vue + Pinia useOrderStore) [Nuxt 3 SSR + Nitro server] ├─ /api/v1/verify.post.ts → Drizzle 조회 + 주문/이심 매칭 └─ /api/v1/activate.post.ts → Maya createEsim → DB insert (esim + plan) ↑ [Drizzle ORM] ←→ [PostgreSQL] [Maya B2B API (Basic auth, $endpoint/esim)]

4 테이블 스키마 (drizzle server/db/schema.ts)

테이블 주요 컬럼 역할 / 신규 앱 관점
order productOrderId(PK), orderId, productOrderStatus, lastChangedType, customerName/Phone, receiverName/Phone, cancel/return 필드들… 네이버 스마트스토어 주문 본체. user_id FK 없음 → 회원 도입 시 추가 필요.
esim esimId(PK=iccid), apn, tag, uid, state, manualCode, smdpAddress, activationCode, networkStatus, serviceStatus, orderId(FK) Maya 가 발급한 회선 자체. 1 order ↔ N esim (quantity 기반).
plan planId(PK), isActivated, activatedAt, timeToBeActivatedInUTC/Local, startDate/Time/TimeZone/Country, networkStatus, dataQuotaBytes, dataBytesRemaining, esimId(FK), planTypeId(FK) 핵심 — esim 1개에 부여된 "활성화 일정 + 사용량 추적" 단위. 잔여 데이터 / 잔여 일수 UI 의 데이터 소스가 여기.
plan-type planTypeId(PK), planNameKr/Eng, planDataTypeKr/Eng, planDataDuration, planCountriesKr/Eng/Iso, timeZones, dataQuotaMb, validityDays, countriesEnabled, policyId/Name… 스마트스토어 옵션코드 ↔ Maya 플랜 매핑. 신규 앱의 카탈로그 출처도 이 테이블 활용 가능.

API 인터페이스 (Nitro)

엔드포인트 입력 동작
POST /api/v1/verify { fullName, phoneNumber, orderId, productOrderId? } order ↔ receiverName/Phone 일치 검증. lastChangedType ∈ {CLAIM_REQUESTED, CLAIM_COMPLETED} 면 cancelled=true. 일치하면 plan-type 조인해 OrderDetails[] 반환.
POST /api/v1/activate OrderDetails + startDate/Time/Country/TimeZone 이미 esim 있으면 400. plan-type 조회 → Maya createEsim N회 (quantity) → DB insert esim + plan(isActivated=false, timeToBeActivated…) → 갱신된 order 반환.

프론트 구조

  • pages — index.vue (주문번호 입력 랜딩) + verify/[orderId].vue + details/[orderId].vue + select-date/[orderId].vue + view/[orderId].vue
  • composables/useApi.ts — verifyOrder() / activateOrder()
  • stores/order.ts — Pinia useOrderStore: orders, singleOrder, isLoading, error + 액션·getter (hasOrders, orderCount, hasEsims 등). React 의 jotai atom 2개를 Pinia 로 단정화 + 에러 상태까지 모델링.
  • components/popup — BaseModal + 7 종 (Alert, Loading, ServerError, NoOrderAlert, CancelledOrderAlert, PullingOrders, IssueQrCodes, ConfirmOrder). React 시절 popup 폴더와 1:1.
  • UI 의존 — @headlessui/vue, @heroicons/vue, vue-tailwind-datepicker, qrcode-vue3. → 신규 앱에선 design-vue 컴포넌트로 점진 대체.
  • runtimeConfig — server: databaseUrl, mayaApiEndpoint, mayaApiClientId, mayaApiClientSecret. public: apiBase = '/api/v1'.
중요 — 현 운영 코드에는 user / user_auth / user_detail 테이블이 없다. 모든 식별은 (orderId + receiverName + receiverPhone) 약한 매칭. 회원 도입은 정말 0에서 출발. 단, order.customerEmail, order.customerPhoneNumber, order.customerName 컬럼이 이미 있어 네이버 주문에서 들어온 고객 식별자로 기존 주문 ↔ 신규 회원 자동 매칭의 기반은 있음.

2.3 NestJS 백엔드 (imjohnkoo/nomacom-esim-manager-v2)

별개 서비스. 네이버 스마트스토어 동기화, 어드민, 결제/취소 큐 처리 등 운영 백오피스 역할 추정. 본 client (nuxt3) 와는 같은 PostgreSQL DB 만 공유하고 HTTP 호출 관계는 없음.

  • NestJS 에 user / user_auth / user_detail 엔티티가 있지만 client DB 에는 해당 테이블이 없음 — 즉 별 DB 또는 별 schema 일 가능성. 확인필요 둘이 같은 DB 라면 client 측 Drizzle 에 user 도 정의해 같이 쓰면 됨. 다른 DB 라면 user 테이블을 client DB 에 신설.
  • api-app-v1 컨트롤러는 비어있음 → client 의 Nitro 가 이미 다 처리. NestJS 측에 새 endpoint 추가할 필요 거의 없음. 새 기능(회원/결제) 도 client Nitro 안에서 끝낼 수 있음 (또는 별 backend 만들지 결정).
  • partner / api-naver-commerce / queue-naver-order 모듈 존재 → 네이버 주문 폴링/큐잉은 NestJS 가 담당.
아키텍처 결정 포인트 — 신규 회원 / 결제 / 보유 이심 관리 백엔드를 어디에 둘지:
  • (A) client Nitro 안에서 다 처리 — 단일 코드베이스, 단일 DB. 단순. 본 초안 가정.
  • (B) NestJS 의 api-app-v1 모듈을 채워서 client 가 호출 — 백오피스/모바일까지 공유, 단 NestJS↔Nitro 2 서비스 동시 운영 부담.
  • (C) 신규 BFF 분리 — 과잉. 비추.
본 rev2 는 (A) 를 가정해 §8 API 표 를 갱신함. (B) 가 결정되면 §8 그대로 NestJS 라우트로 옮기면 됨.

3.1 공통 UX 패턴 (벤치마크 종합)

  • 5분 안에 첫 가치 — 앱 열어서 첫 QR 까지 ≤ 5 화면, ≤ 60초.
  • 플랜 카드 = 가격, 데이터, 기간, 국가, 활성화 조건 5요소로 압축.
  • 설치 가이드는 항상 옆에 — QR 다운로드 + iOS 다이렉트 링크 + 안드로이드 매뉴얼 입력 (SM-DP+ / 활성화 코드).
  • 실시간 잔여 데이터 / 잔여 일수 가 홈 카드의 1순위 정보.
  • 실패는 명시적 — "통신사 / 기기 호환 안됨", "결제 실패", "Maya 응답 지연" 등 모두 별도 화면/팝업.
  • 고객 지원 1탭 — 챗(또는 카톡채널) 진입을 모든 상태 화면에서 노출.

4. 신규 기능 범위

핵심 기능 4개 (회원가입/로그인, 자체 이심 발급, 보유 이심 관리, 게스트 흐름 유지) 외에 부가 기능들의 P0/P1/P2 분류.

4.1 회원가입 / 로그인 P0

  • 채널: 휴대폰번호(OTP) · 이메일+PW · Apple · Kakao · Naver. 1차 P0: 휴대폰 OTP + Kakao + Apple. Naver / Email-PW 는 P1.
  • 본인확인: 휴대폰 OTP만으로 1차. PASS / NICE 본인인증은 결제 본격화 시 P1.
  • 게스트 → 회원 전환: v1 흐름 끝에서 "이 이심을 내 계정에 저장하시겠습니까?" CTA → 휴대폰번호 일치 기준으로 자동 매칭.
  • 세션: HttpOnly cookie + refresh token rotate. NOMACOM_LOGIN_JWT_SECRET 키 별도 (ssm-paths.md 의 secret naming 원칙).

4.2 이심 발급 P0

  • 카탈로그: 국가/지역 → 데이터/기간 → 정렬(인기/가격/데이터). Maya get_esim_plans 기반.
  • 플랜 상세: 가격, 데이터, 기간, 활성화 정책(우리 정책 — 회선 ON 시점 활성화, 24h 갱신, 소진 후 속도 옵션), 호환 기기 안내.
  • 결제: 카카오페이 / 네이버페이 / 카드(아임포트 또는 토스페이먼츠). P0 후보: 토스페이먼츠(통합 PG, 가맹 신청 단순).
  • 이심 발급: 결제 성공 → Maya create_esim → DB esim 적재 → 즉시 QR + LPA 표시. 백엔드 v1 의 /activate 와 통합.
  • 활성화 시점 선택: "지금 활성화" / "도착 시 자동 활성화" 2 옵션 (Ubigi SmartStart 패턴 + v1 의 국가/날짜/시간 지정 패턴 융합).

4.3 보유 이심 관리 P0

  • 내 이심 목록: 활성/만료/대기 분류. 카드형(데이터 잔량 게이지 + 국기 + D-day).
  • 상세: 잔여 데이터, 잔여 기간, 사용 국가, 활성화 / 정지, QR 재표시 (이미 설치된 경우 LPA 복사), 토픽업(P1).
  • 이심 추가 등록: 다른 채널 (스마트스토어 게스트 발급분) 을 내 계정에 끌어오기. orderId + receiverPhoneNumber 일치 매칭.
  • 설치 가이드: iOS Universal Link 즉시 설치(모바일 앱 한정), 웹은 QR + 매뉴얼 코드.

8.3 환경 변수 / SSM

nuxt3 코드의 runtimeConfig 키 (databaseUrl / mayaApiEndpoint / mayaApiClientId / mayaApiClientSecret) 는 그대로 유지. 추가될 키:

  • /nomacom/shared/maya/* — 기존 유지.
  • /nomacom/shared/db/DATABASE_URL — 기존 유지.
  • /nomacom/client/NOMACOM_LOGIN_JWT_SECRET — 신규. 세션 쿠키 서명.
  • /nomacom/client/OAUTH_KAKAO_CLIENT_ID · _CLIENT_SECRET · _REDIRECT_URI
  • /nomacom/client/OAUTH_APPLE_* — Apple Sign In (private key JWK 포함)
  • /nomacom/client/OAUTH_NAVER_* — (P1)
  • /nomacom/client/TOSSPAYMENTS_CLIENT_KEY · _SECRET_KEY — (P1-β)
  • SOLAPI(SMS OTP) — A 안 채택 시 client 측이 직접 호출. backend 의 /nomacom/shared/solapi/* 키 공유 가능 (read-only IAM 추가 필요) 또는 client 전용 별도 발급.

local 개발은 apps/client/.env.local (gitignore). nuxt3 코드는 yarn dev --dotenv .env.local 패턴을 이미 사용 중.

9. 모바일 앱 전략

9.1 동일 IA · 동일 디자인 토큰 · 분리된 컴포넌트

  • 웹앱과 1:1 IA. 화면 이름, URL/스택, 카드 구성 동일.
  • RN 컴포넌트는 design-vue 의 prop 이름과 최대한 align (e.g. NButton ↔ NButtonRN 의 variant/size 동일).

9.2 차별 포인트 — iOS 17.4+ Universal Link

  • memory: future_mobile_app_esim_install 에 명시. CoreTelephony entitled API 는 MVNO 라 불가.
  • 대신 Apple Universal Link (esimsetup.apple.com) 로 1탭 설치. 이미 모바일 깡통에 데모 코드 있음.
  • 안드로이드는 EasyTransfer 미보장 → QR + LPA 복사가 fallback.

9.3 빌드 / 배포

  • Expo Managed (bare 금지, CLAUDE.md 명시).
  • EAS Build + OTA. EAS Secrets 채널로 API URL, OAuth client key.
  • CodeDeploy 파이프라인과는 분리 — 별도 GHA workflow (현재 미구축, weekly B 트랙 차주 이후).

9.4 웹 PWA vs 네이티브 앱 우선순위

결정 필요 — 다음 옵션 중 하나로 정렬:
  • (A) 웹 우선 + PWA — 1~2 phase 는 Nuxt 만, 모바일은 깡통 유지. 가장 빠른 가치 증명.
  • (B) 듀얼 트랙 — 같은 phase 안에 웹/모바일 함께. 디자인 토큰 강제 동기화 + 백엔드 인터페이스 부담.
  • (C) 모바일 우선 — Universal Link 1탭 설치라는 USP 를 빨리 노출. 단, 결제·OAuth 의 in-app 검토(Apple) 마찰.
본 초안은 (A) 를 기본 가정으로 phase 를 짰음.
